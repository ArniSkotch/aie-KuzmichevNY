Проект решает задачу фонемного выравнивания (phoneme alignment) для речевых записей: по аудиофайлу определяется последовательность фонем и их временные границы.

## 2. Постановка задачи и контекст

Опишите:

1. **Предметную область и задачу:**
   - Задача — **фонемное выравнивание речи** (phoneme/forced alignment): по аудиозаписи устной речи получить временную разметку — последовательность фонем с границами начала и конца каждой.
     Это классическая задача в речевых технологиях, нужная, например, для разметки обучающих корпусов TTS/ASR, анализа произношения (в т.ч. для приложений обучения языку),
     караоке/субтитров на уровне звуков и для последующего извлечения фонемных признаков в других речевых моделях.
   - Потенциальный пользователь сервиса — исследователь или инженер, который хочет получить автоматическую фонемную разметку набора аудиозаписей без ручной аннотации,
     либо использовать `/predict` как шаг в более крупном речевом пайплайне (например, для последующей оценки качества синтезированной речи).

2. **Формулировку задачи в терминах ML/ИИ:**
   - **Вход:** аудиофайл (`.wav`/`.flac`/`.ogg`/`.mp3`), приводится к частоте дискретизации 16 кГц перед подачей в модель.
   - **Выход:** список сегментов `{"phoneme": str, "start_time": float, "end_time": float}` — фонема и её границы в секундах.
   - **Модель:** CTC-классификатор фреймов (Wav2Vec2ForCTC), фрейм длиной 0.02 с;
     финальные границы сегмента получаются группировкой одинаковых argmax-токенов подряд и (в улучшенном варианте) последующей акустической коррекцией.
   - **Ограничения:**
     - инференс должен укладываться в разумное время для одного аудиофайла в синхронном HTTP-запросе (`/predict` — без батчинга и без очереди задач);
	 - модель используется «из коробки», без дообучения — ограничение по времени проекта;
	 - точность границ важнее, чем скорость работы постобработки (коррекция границ — лёгкая операция на CPU через `librosa`).

3. **Целевые метрики качества:**
   - Используется набор метрик, охватывающий и качество распознанной *последовательности* фонем, и качество *временных границ* — потому что это две разные грани задачи выравнивания:
   
   - **PER (Phoneme Error Rate)** — доля ошибок (замены + вставки + удаления) относительно числа эталонных фонем;
     основная метрика качества распознавания последовательности, аналог WER для фонем.
   - **Phoneme Precision / Recall / F1** — насколько предсказанные фонемы соответствуют эталонным после выравнивания последовательностей (Левенштейн).
   - **Boundary MAE / RMSE (start, end, center)** — средняя ошибка границ сегмента в секундах для совпавших по метке фонем;
     показывает, насколько точно во времени поставлены границы, чего PER не отражает вообще.
   - **Boundary exact accuracy @10/20/50 мс** — доля совпавших фонем, у которых обе границы (начало и конец) попали в заданный допуск;
     стандартный способ отчитываться о качестве forced alignment в литературе.
   - **Segment IoU (mean/median)** — пересечение по объединению предсказанного и эталонного интервала фонемы;
     единая безразмерная метрика «насколько хорошо предсказанный интервал перекрывает эталонный», устойчивая к выбору конкретного порога допуска.

   - Эти метрики реализованы в `src/models/metrics.py` (`compute_metrics`, `summarize_metric_rows`) и покрыты unit-тестами в `tests/test_metrics.py`.

## 3. Данные

Опишите, какие данные использует проект:

1. **Источник данных:**
   - Открытый датасет **TIMIT** (DARPA TIMIT Acoustic-Phonetic Continuous Speech Corpus), зеркало на Kaggle: `mfekadu/darpa-timit-acousticphonetic-continuous-speech`.
     TIMIT — стандартный корпус для задач фонемного распознавания и выравнивания: записи носителей 8 диалектов американского английского (`DR1`–`DR8`) с ручной разметкой фонемных границ.

2. **Структура данных:**
   - Исходный TIMIT: на каждую запись — `.WAV` (аудио), `.PHN` (построчно `start_sample end_sample phoneme`) и `.TXT` (`start_sample end_sample транскрипт`).
   - После конвертации (`src/data/build_dataset.py::build_dataset`) — унифицированный формат:
     - `data/processed/input_audio/audio/<file_id>.wav`;
     - `data/processed/input_audio/annotations/<file_id>.json` с полями `file_id`, `transcript`, `sample_rate`, `speaker_id`, `dialect`, `split`, `utterance`,
       `audio_path`, `segments` (список `{"phoneme", "start_time", "end_time"}`).
   - Ключевые признаки для анализа: длительность записи, число фонем на файл, частота встречаемости конкретных фонем, диалект и спикер (извлекаются из имени файла вида `TRAIN_DR2_MCPM0_SI552`).

3. **Предобработка и EDA:**
   - Предобработка (`src/data/build_dataset.py`):
     - парсинг `.PHN` → сегменты с таймингами в секундах (деление номера сэмпла на частоту дискретизации TIMIT, 16 кГц);
     - парсинг `.TXT` → текстовый транскрипт;
     - дедупликация WAV-файлов по имени, случайная выборка `max_files` файлов с фиксированным `random_seed` для воспроизводимости и покрытия всех 8 диалектов;
     - перезапись аудио через `soundfile`/`librosa`, сохранение в единый `.wav`.
   
   EDA выполнен модулем `src/eda.py` (вызывается из ноутбука `notebooks/exp04_voice_phoneme_pipeline.ipynb`, разделы 2 и 2.1–2.2):
   
   - Распределение длительностей аудиозаписей (большинство файлов короче ~4 с — типично для TIMIT, где это отдельные короткие фразы);
   - Топ-20 самых частых фонем и их доля от общего числа вхождений;
   - Распределение записей по диалектам и количество фонем на файл;
   - После прогона модели — гистограмма PER по файлам, boxplot ошибок границ (start/end/center MAE), таблица топ-5 худших файлов по PER.
   
   - Важное наблюдение: PER на уровне датасета получился высоким (~0.70, см. раздел 5) — это ожидаемо, так как модель `wav2vec2-lv-60-espeak-cv-ft` обучена предсказывать espeak-фонемы (IPA-подобный набор символов),
     а эталонная разметка TIMIT использует собственную (ARPAbet-подобную) нотацию фонем; без явного маппинга одного набора символов в другой даже корректно распознанные звуки засчитываются как несовпадения по метке.
	 Это зафиксировано как ограничение проекта (раздел 8).

## 4. Модели и подходы

Опишите, какие модели вы пробовали и как развивался ваш подход:

1. **Базовые (baseline) модели:**
   - В проекте используется **одна предобученная модель** — `facebook/wav2vec2-lv-60-espeak-cv-ft` (Wav2Vec2ForCTC + Wav2Vec2Processor из HuggingFace `transformers`), без дообучения.
     Это сознательное решение в рамках доступного времени проекта: вместо сравнения разных архитектур/моделей мы сравниваем **два варианта постобработки одного и того же CTC-вывода** (см. ниже).
     Это даёт честное покомпонентное сравнение без шума от случайности обучения.
   - Базовый («baseline») вариант: argmax по CTC-логитам, группировка одинаковых токенов подряд -> сырые границы фонем напрямую из позиций фреймов (шаг кадра 0.02 с),
     без какой-либо коррекции (`src/compare_models.py::_ctc_decode`, и идентичная логика в `src/models/inference.py::extract_and_save_phonemes`).

2. **Улучшенные модели и эксперименты:**
   - «Improved»-вариант берёт те же сырые CTC-сегменты и уточняет их границы акустически: `librosa.effects.split`/`trim` находит интервалы сигнала, не являющиеся тишиной (`top_db` — порог из `config.yaml`),
     и граница фонемы «подгоняется» к границе ближайшего акустически активного интервала, а конец сегмента — к началу следующего сегмента в том же интервале либо к концу интервала (`src/models/inference.py:: correct_segment_boundaries`).
     Состав фонем (последовательность меток) при этом не меняется — меняются только тайминги.
   - Использованный таким образом метод не требует обучения и дополнительных гиперпараметров, кроме одного порога `top_db` (зафиксирован в `config.yaml`, значение 35 дБ).

3. **Нейросетевые модели (если применимо):**
   - **Архитектура:** Wav2Vec2 (self-supervised speech encoder) + CTC-голова, версия `lv-60-espeak-cv-ft` — предобучена на 60 тыс. часов многоязычной речи (LibriVox) и дообучена на espeak-фонемизированных транскриптах из Common Voice.
     Модель и токенизатор загружаются один раз при старте (`src/models/model_loader.py`).
   - **Обучение:** в проекте не проводится — используется готовый чек-пойнт в режиме `model.eval()` / `torch.no_grad()`.
	 Из «настроек обучения» к проекту относится только частота дискретизации входа (приведение к 16 кГц) и длина фрейма CTC (0.02 с, фиксируется конфигом и используется при пересчёте индексов фреймов в секунды).

Эксперименты по сравнению вариантов реализованы в `src/compare_models.py` и запускаются из ноутбука `notebooks/exp04_voice_phoneme_pipeline.ipynb`, раздел 7.

## 5. Экспериментальный протокол и результаты

Здесь важно показать, что выбор финальной модели был осмысленным.

1. **Экспериментальный протокол:**
   - Отдельного train/val/test разбиения не требуется, так как модель не обучается — оценка идёт на всех файлах, прошедших подготовку данных (TIMIT, случайная подвыборка, см. раздел 3).
   - Каждый аудиофайл прогоняется через модель **один раз** (`_ctc_decode`), и из одного и того же набора сырых сегментов строятся два варианта:
     `baseline` (без изменений) и `improved` (после `correct_segment_boundaries`). Это устраняет вариативность, связанную с повторными прогонами модели, и делает сравнение «по компоненту» (постобработка) максимально честным.
   - Для каждого варианта эталонная разметка подгружается через `src/features/annotation_loader.py`, метрики считаются функцией `compute_metrics` (допуски по границам: 10/20/50 мс,
	 заданы в `config.yaml` -> `processing.tolerance_ms`), затем агрегируются по всем файлам (`summarize_metric_rows`).
   - По факту запуска (`src/compare_models.py::run_both_variants`) обработано **150 файлов** (`files_processed = 150`).

2. **Сравнение моделей по метрикам:**

   Пример таблицы (адаптируйте под свои метрики):

   | Вариант / конфигурация      | Описание                                                                     | PER    | Phoneme F1 | Boundary Exact Accuracy @20 мс | Boundary Exact Accuracy @50 мс | Segment IoU (mean) | Комментарий                        |
   |-----------------------------|------------------------------------------------------------------------------|--------|------------|--------------------------------|--------------------------------|--------------------|------------------------------------|
   | **Baseline**                | Wav2Vec2-LV60, сырые CTC-границы, без постобработки                          | 0.6987 | 0.3448     | 0.2847                         | 0.7601                         | 0.3267             | Стартовая точка: только argmax CTC |
   | **Improved**                | Wav2Vec2-LV60 + акустическая коррекция границ (`librosa.effects.split/trim`) | 0.6987 | 0.3448     | 0.2795                         | 0.8068                         | 0.4671             | Финальный вариант                  |
   | **Δ (improved − baseline)** | —                                                                            | 0.0000 | 0.0000     | −0.0052                        | **+0.0467**                    | **+0.1404**        | —                                  |

Наблюдения:

   - **PER и Phoneme F1 не изменились** — ожидаемо, так как постобработка трогает только тайминги, а не последовательность распознанных меток фонем.
   - **Boundary Exact Accuracy @20 мс** у `improved` чуть ниже (0.2795 против 0.2847, −0.0052).
     На самом строгом допуске акустическая коррекция иногда «передвигает» границу дальше от истинной, чем сырое CTC-предсказание.
   - **Boundary Exact Accuracy @50 мс** заметно выше у `improved` (0.8068 против 0.7601, +0.0467) — при более мягком допуске коррекция чаще попадает в нужный интервал.
   - **Segment IoU mean** улучшилась сильнее всего (0.4671 против 0.3267, +0.1404) — предсказанные интервалы в среднем заметно точнее перекрывают эталонные.

3. **Выбор финальной модели:**
   - Финальным вариантом, используемым в `/predict` (`src/service/api.py`), выбран **`improved`** (CTC + акустическая коррекция границ). Аргументы:
     - PER и F1 не страдают — коррекция «бесплатна» в смысле качества распознавания меток;
     - существенный рост IoU (+0.14) и точности при более реалистичном допуске 50 мс (+0.047) — для большинства практических применений (разметка для downstream-задач, визуализация границ)
	   это важнее, чем выигрыш на самом строгом 20-миллисекундном допуске;
     - небольшая просадка на допуске 20 мс (−0.005) признаётся как осознанный trade-off, а не недостаток, который мы скрываем — он зафиксирован в выводах эксперимента и в ограничениях проекта (раздел 8).

## 6. Архитектура решения и сервис

Опишите, как из модели получился работающий сервис:

```
TIMIT (Kaggle) ──download_timit.py── extracted TIMIT (.WAV/.PHN/.TXT)
                                              │
                                     build_dataset.py
                                              │
                         data/processed/input_audio/{audio,annotations}
                                              │
                  ┌───────────────────────────┼───────────────────────────┐
                  │                           │                           │
            eda.py (EDA)            run_pipeline.py (batch)      compare_models.py (эксперимент)
                  │                           │                           │
                  │            model_loader.py + inference.py + metrics.py│
                  │                           │                           │
              графики EDA          metadata.json, metrics_summary.json    model_comparison.* ,
                                                                            графики сравнения
                                              │
                                     src/service/api.py (FastAPI)
                                       /health   /predict
```

Все компоненты переиспользуют одни и те же функции из `src/models/` и `src/features/annotation_loader.py`.
Логика CTC-инференса и акустической коррекции не продублирована между ноутбуком, batch-пайплайном, экспериментом сравнения и сервисом.

Реализован FastAPI-сервис `src/service/api.py`:

  - `GET /health` — возвращает `{"status", "model_loaded", "model_id"}`, позволяет убедиться, что сервис поднят и модель загружена.
  - `POST /predict` — принимает `multipart/form-data` с полем `file`
    (`.wav`/`.flac`/`.ogg`/`.mp3`), внутри:
    1. читает байты файла во временный `.wav`;
    2. ресемплирует в 16 кГц (`librosa.resample`);
    3. прогоняет через Wav2Vec2 CTC, получает сырые сегменты;
    4. применяет акустическую коррекцию границ (`correct_segment_boundaries`) — то есть отдаёт именно «improved»-вариант, выбранный по результатам раздела 5;
    5. возвращает JSON `{"source_file", "phoneme_count", "segments": [...]}`.
  - Неподдерживаемое расширение файла -> `415`, внутренние ошибки -> `500` с описанием.

Swagger UI доступен на `/docs`. Сервис можно запускать как отдельный процесс (`python -m src.service.api`) либо в фоновом потоке прямо из ноутбука (`run_in_background()`), без блокировки остальных ячеек.

- **ML/аудио:** `torch`, `transformers` (Wav2Vec2ForCTC/Processor), `librosa`, `soundfile`, `phonemizer` (espeak-фонемизация транскриптов без таймингов).
- **Сервис:** `fastapi`, `uvicorn[standard]`, `python-multipart`, `nest_asyncio` (для запуска сервиса внутри ноутбука).
- **Данные/конфиги:** `pandas`, `numpy`, `pyyaml`, `python-dotenv`, `kaggle` (скачивание TIMIT).
- **Визуализация:** `matplotlib`.
- **Тесты:** `pytest`.
- **Docker:** на данный момент не используется — сервис запускается напрямую в виртуальном окружении (см. README.md, раздел 4.2).
  Это зафиксировано как ограничение текущей версии (раздел 8).

## 7. Наблюдаемость, конфигурация и безопасность

Кратко опишите:

1. **Логи и наблюдаемость:**
   - Единый формат логирования для всего проекта — `src/logging_utils.py::setup_logger` (`%(asctime)s [%(levelname)s] %(name)s: %(message)s`),
     используется и в batch-пайплайне, и в эксперименте сравнения, и в сервисе.
   - Логируются: старт обработки каждого файла, ошибки обработки конкретного файла (с `exc_info` для трассировки),
     сводные метрики по датасету, события сервиса (`GET /health`, `POST /predict`, включая имя файла и размер запроса, и ошибки).
   - Базовая проверка работоспособности сервиса — эндпоинт `GET /health`, который явно показывает, что модель загружена (`model_loaded: true`) и какая именно (`model_id`).

2. **Конфигурации:**
   Все параметры, которые имеет смысл менять без правки кода, вынесены в `configs/config.yaml`:
   
   - пути к данным и артефактам (`paths.*`);
   - идентификатор модели, длина CTC-фрейма, порог тишины для коррекции границ (`model.*`);
   - допустимые расширения аудио/аннотаций, частота дискретизации (`audio.*`);
   - сколько файлов обрабатывать при сборке датасета, допуски для метрик границ (`processing.*`);
   - хост/порт сервиса (`service.*`);
   - переменные окружения — зеркало HuggingFace, бэкенд `torchaudio`, путь к eSpeak NG (`env.*`), которые `src/env_setup.py::apply_environment` выставляет **до** первого импорта `torchaudio`/`transformers`.
   
3. **Безопасность:**
   - Единственный секрет в проекте — учётные данные Kaggle API (`KAGGLE_USERNAME`, `KAGGLE_KEY`), нужные только для скачивания TIMIT.
   - Хранятся в `configs/.env`, который **не коммитится**: `src/setup_project.py` при первом запуске создаёт шаблон `configs/.env.example` и добавляет `configs/.env` в `.gitignore`, если его там ещё нет.
   - В `configs/config.yaml` секретов нет — там только публичные пути и идентификаторы (зеркало HuggingFace, путь к локально установленному eSpeak NG).

## 8. Ограничения и дальнейшая работа

Будьте честны:

- Честно зафиксированные ограничения текущей версии:
  - **Несовпадение фонемных алфавитов.** Модель предсказывает espeak-фонемы, эталон TIMIT использует свою нотацию — без явного маппинга это раздувает PER (~0.70)
    даже при субъективно неплохом качестве распознавания звуков. Маппинг между алфавитами не реализован из-за ограничений по времени.
  - **Подвыборка датасета.** Эксперименты проводились на части TIMIT (до 300 файлов в EDA, 150 — в сравнении baseline/improved), а не на полном корпусе.
  - **Модель не дообучалась** на TIMIT — используется готовый чек-пойнт.
  - **Коррекция границ — простая эвристика** (порог тишины + привязка к соседним сегментам), а не обучаемый или statistically optimal алгоритм;
    отсюда и компромисс: рост IoU/допуска 50 мс при небольшой просадке на допуске 20 мс.
  - **Нет Docker-образа** для развёртывания сервиса.
  - **Сервис без батчинга, авторизации и хранения истории запросов** — обрабатывает ровно один файл за один запрос.

- Что было бы сделано при наличии большего времени:
  - **Модель:** построить/использовать маппинг espeak-фонем в нотацию TIMIT перед расчётом PER, чтобы метрика отражала реальное качество распознавания звуков,
    а не расхождение алфавитов; попробовать дообучение Wav2Vec2 на TIMIT.
  - **Сервис:** добавить Dockerfile и docker-compose, батч-обработку запросов, простую авторизацию.
  - **Данные/эксперименты:** прогнать сравнение baseline/improved на полном TIMIT, добавить более сильный алгоритм коррекции границ
    (например, forced alignment с динамическим программированием с учётом длительностей фонем вместо эвристики на основе тишины).

## 9. Сценарий демонстрации на защите

Опишите, как вы планируете демонстрировать проект:

1. Что вы **запускаете**:
   - демонстрационный ноутбук `notebooks/exp04_voice_phoneme_pipeline.ipynb` — последовательно показывает подготовку данных, EDA, инференс и эксперимент сравнения;
   - сервис — `python -m src.service.api` (или `run_in_background()` из ноутбука, раздел 6), доступен на `http://localhost:8000`, Swagger UI на `/docs`.
2. Какие **1-2 ключевых сценария** вы показываете:
   - **Запрос к `/predict`:** загружается реальный `.wav` из TIMIT, сервис возвращает список фонем с таймингами (`GET /health` — для проверки, что модель действительно загружена, не заглушка).
   - **Сравнение baseline vs improved:** показывается итоговая таблица метрик и график `model_comparison_plot.png` (раздел 5) — наглядно видно,
	 что PER не изменился, а Boundary Exact Accuracy @50 мс и Segment IoU существенно выросли при незначительной просадке на допуске 20 мс, что и обосновывает выбор `improved` как финального варианта.
3. На что хотите, чтобы преподаватель обратил внимание:
   - что `/predict` действительно прогоняет аудио через Wav2Vec2 и применяет именно ту акустическую коррекцию, которая была обоснована экспериментом, а не возвращает случайные/заглушечные значения;
   - на обоснованность выбора финального варианта по конкретным цифрам, включая честное признание trade-off (просадка на допуске 20 мс), а не только «улучшение по всем метрикам»;
   - на структуру `src/` — переиспользование одной и той же логики инференса между ноутбуком, batch-пайплайном, экспериментом сравнения и сервисом.

Команды для запуска — см. `project/README.md`, разделы 3–4.
